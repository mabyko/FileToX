## 판단의 출발점

네 문제의 원인이 다르다. FFmpeg는 배포한 실행 환경의 기능 문제, 엄격 비교는 무엇을 보존해야 하는지의 판정 문제, SVG는 렌더러의 표현 범위 문제, AVIF는 매번 경쟁 후보를 만드는 실행 구조의 비용 문제다. 하나의 새 라이브러리로 네 문제를 해결할 수 있다는 근거는 없다.

기존 수치의 근거는 [최종 검증 보고서](../design/engine-differential-triage.md#quality-follow-up-and-alternatives-2026-10-26)다. 849건의 63건 실패와 C# 엄격 비교 48건 FAIL은 서로 다른 집계이며, 이번 연구로 수치를 바꾸지 않는다.

## 1. FFmpeg: 실행 파일의 존재에서 지원 기능의 보장으로

확인한 FFmpeg는 Homebrew `9.0.2`이고 실제 검증에서도 사용됐다. 앱이 선택하는 `libvorbis`, `libtheora`, `libopencore_amrnb`는 이 실행 파일에 없다. `vorbis`라는 다른 인코더가 있다는 사실만으로 `libvorbis` 요청이 성공하지는 않는다. [출력 설정](../../Sources/Engine/Engines/Media/MediaEncoding.swift)

| 방향 | 이점 | 한계 | 판단 |
| --- | --- | --- | --- |
| 사용자 설치 FFmpeg + 기능 사전 확인 | 설치 용량과 유지 작업이 작음 | 부족한 기능을 알려줄 뿐 제공하지 못함 | 사용자 지정 경로를 위한 보조 기능 |

| libav* 직접 연결 | 프로세스 경계와 전달 비용을 줄일 가능성 | 기존 프로세스 격리·취소 구조와 통합을 다시 검증해야 함 | 현재 21건의 원인에 비해 변경 범위가 큼 |

현재 [ManagedEngineInstaller](../../Sources/Engine/Infrastructure/ManagedEngineInstaller.swift)는 Pandoc·LibreOffice·Calibre를 위한 다운로드·크기/해시 확인·staging·배치 경로를 이미 제공한다. 이 기반에 macOS arm64용 FFmpeg 묶음을 추가하는 쪽을 우선 권장한다. 새 설치기를 만들 필요는 없지만, 검증된 macOS 바이너리와 배포 자료를 확보하는 일은 남는다. 실행 파일·라이브러리·버전·빌드 옵션·지원 인코더·고지를 함께 고정해야 한다. 사용자 지정 실행 파일은 실제 기능에 따라 지원 범위를 표시하고 명시적인 선택을 임의로 바꾸지 않는다.

Homebrew의 실행 파일을 그대로 복사하는 것으로 이 묶음을 완성할 수는 없다. 배포 폴더 밖의 Homebrew 동적 라이브러리에 의존하지 않는 재배치 가능한 arm64 산출물과, 기존 실행 파일 확인에 더한 필수 코덱 검사가 필요하다. 현재 출력 표의 x264·OpenCORE AMR을 유지하는 빌드 구성을 기준으로 배포 자료를 준비한다. 인코더를 바꾸는 대안은 품질 설정의 의미도 바꾸므로 별도 검증 대상이다.

더 작은 임시 대안도 있다. Homebrew의 일반 `ffmpeg` 대신 필요한 세 라이브러리가 포함된 `ffmpeg-full`을 선택하도록 안내할 수 있다. 다만 `ffmpeg-full`은 keg-only이고 현재 앱 탐색에는 그 전용 경로가 없으므로 안내문 교체만으로 자동 발견을 보장하지 않는다. 지금 앱의 `brew install ffmpeg` 안내는 요구 인코더와 맞지 않는다. 이 대안은 개인 환경의 해결책이며, 앱이 동일한 기능을 제공하는 관리형 묶음의 대체 보장은 아니다. 사용자 Mac의 설치나 설정은 이번에 변경하지 않았다.

단순히 지원하지 않는 항목으로 다시 분류하는 것은 변환 기능의 개선으로 세지 않는다. 63건을 다음 작업으로 나눠야 한다.

- 인코더 누락 21건: 해당 인코더가 있는 묶음에서 실제 출력까지 검증한다.
- PML 7건: 앞서 단순 미지원으로 분류했지만, Claude 검토와 공식 소스 대조에서 더 직접적인 원인을 찾았다. Calibre 9.15.0의 `PMLOutput`은 `file_type = 'pmlz'`이며 `index.pml`과 `index_img`를 ZIP에 넣는다. 앱의 출력 표는 `pml`이다. 우선 PMLZ 생성 후 PML·참조 그림을 함께 게시하는 어댑터를 검증해야 한다. 확장자만 바꾸거나 PML 파일 하나만 추출해서는 안 된다. 실제 7건의 성공은 아직 실행으로 확인하지 않았다.
- 중간 PDF에 텍스트가 없는 17건: 원본 PDF 17개가 모두 OCR을 필요로 한다는 뜻이 아니었다. 실제 ID를 다시 읽으면 이미지·영상 출발 15건, SVG 1건, PDF 옵션 표본 1건이다. 픽셀의 글자를 TXT로 읽으려면 OCR이 필요하지만, 그림을 담을 수 있는 ODT·EPUB 등의 출력은 그림·페이지를 보존하는 경로가 대안이다. `auto-087-svg-to-odt`는 원본에 텍스트가 있는데 SVG→PDF에서 glyph outline이 돼 다음 단계가 읽지 못하는 사례다. 이 경우는 텍스트를 보존하는 중간 경로나 직접 어댑터를 먼저 검증한다.
- 오디오 없는 입력 14건: 오디오 추출 요청의 입력 조건을 확인한다. 없는 오디오를 정상 결과로 만들 수는 없다.
- FFmpeg 무출력 3건·PPSX→AZW3 링크 오류 1건: 재현 가능한 실제 변환 결함으로 따로 해결한다.

**채택 기준:** 새 FFmpeg 구성에서 21건의 실제 출력과 필수 스트림·컨테이너가 유효해야 한다. 기존 정상 미디어 표본에도 새 결함이 없어야 한다. PML 7건은 본문·비ASCII 문자·그림 참조·sidecar 게시까지 확인한다. 실행 전 안내로 바뀐 경우와 실제 변환 성공을 별도 집계한다. 빌드 구성의 재배포 조건은 공식 고지와 구성별로 확인한다.

경로 선택도 형식 ID만으로 결정하지 않는 것이 핵심이다. 현재 [RoutePlanner](../../Sources/Engine/Core/Conversion/RoutePlanner.swift)는 출발·도착 형식과 비용으로 경로를 선택한다. 각 단계가 텍스트·페이지·그림·오디오를 요구하는지, 보존하는지, 잃는지를 표현하고 최종 출력에 필요한 조건을 만족하는 경로를 고르는 확장이 필요하다. 이는 모든 문서를 하나의 거대한 내부 모델로 다시 쓰는 제안과는 범위가 다르다. 보존된 `replay-validation/replay-fresh/run.json`의 17개 오류와 [SVG PDF의 glyph outline 동작](../../Sources/Engine/Engines/Vector/SvgRenderer.swift)을 근거로 한 설계 제안이다.

현재 [PdfDocumentReader](../../Sources/Engine/Engines/Pdf/PdfDocumentReader.swift)에도 그림을 빼고 읽는 `readText`와, 텍스트 없는 페이지를 그림으로 넣는 문서용 경로가 구분돼 있다. 따라서 이미지 출발 15건을 일괄로 불가능하다고 분류하면 안 된다. 각 최종 형식까지 대체 경로가 연결되는지는 별도로 확인해야 한다. 영상·다중 프레임에서 어느 프레임을 문서에 넣을지는 의도가 확정되지 않은 항목으로 남긴다.

**PML의 별도 품질 한계:** 공식 `PMLMLizer.clean_text`는 비ASCII 문자를 `unipmlcode`로 바꾸고, 이 함수는 허용 목록 밖의 문자를 `?`로 만든다. 한글은 그 목록에 없다. 이 처리는 최종 파일 인코딩보다 앞서므로 `pml_output_encoding`을 UTF-8로 바꾸는 것만으로 해결되지 않는다. PMLZ 연결을 고친 뒤에도 한글 보존 문제는 남는다. 지원할 문자와 읽기 도구의 규약을 검증한 writer 보완이 필요하며, 단순히 파일이 생성됐다고 7건을 품질 합격으로 세지 않는다.

**작은 재현 실험으로 좁힐 두 가설:** TS/M2TS 무출력은 [대표 프레임 추출](../../Sources/Engine/Engines/Media/MediaEncoding.swift)이 입력 앞 `-ss`로 길이의 10% 지점을 찾는 동작과 관련됐을 가능성이 있다. 처음부터 디코딩한 뒤 같은 목표 시점의 프레임을 선택하는 대조가 다음 확인이다. 첫 프레임으로 대체한다면 선택 정책도 바뀌므로 별도로 다룬다. PPSX→AZW3는 중간 문서·EPUB에서 슬라이드 본문이 사라지는지 먼저 확인한다. 어느 가설도 이번 연구에서 원인을 실행으로 확정하지 않았다.

## 2. 검사: C#와의 차이와 원본 보존을 각각 기록

48건을 모두 동일하게 보이도록 만드는 목표는 실제 품질과 충돌할 수 있다. 이미 AVIF에서는 C# 결과와 더 달라졌지만 원본 색 보존이 좋아진 사례가 있다. 반대로 메타데이터 차이 14건에서 본문이 같았다는 사실은 제목·저자·표지·구조까지 정상이라는 증거가 아니다.

권장하는 것은 변환 엔진 전체를 새 공통 문서 모델로 다시 만드는 일이 아니다. 우선 검사 도구에서 형식별로 작은 보존 규약을 정의한다.

1. 본문·페이지·읽기 순서·목차·내부 링크의 대상.
2. CSS의 실제 적용 순서, 표지 및 참조 이미지, 크기와 배치.
3. 제목·저자·언어·의미 있는 날짜, 이미지의 ICC·EXIF·XMP.
4. 출력 형식이 표현할 수 없어 의도적으로 바뀌는 요소.

한 사례에는 기존 엄격 비교 판정, 보존 규약의 판정, 근거, 미확인 항목을 함께 둔다. 생성 UUID나 생성 시각만 역할을 확인한 뒤 별도로 다룬다. 모든 날짜를 지우거나 CSS·spine을 정렬하는 식의 정규화는 허용하지 않는다.

Claude는 `pptx→lit`의 두 결과가 함께 빈 본문일 가능성도 제기했다. 보존 보고서에는 본문 요소 0개·텍스트 노드 1개와 본문 비율 1.0이 있지만 그 텍스트 노드의 실제 값은 확인되지 않았다. 따라서 확정된 손실로 발표하지 않고, 입력 슬라이드의 알려진 문장이 출력에 존재하는지를 다음 검사로 삼는다. 두 구현이 같다는 사실만으로 원본 보존을 증명하지 못하는 이유다.

검사 도구가 실제 손실을 잡는지 확인할 음성 표본도 필요하다. 읽기 순서 뒤집기, 참조 그림 제거, 제목 변경, CSS cascade 변경, 링크 대상 삭제는 반드시 실패해야 한다. 일관되게 이름만 바꾼 리소스 ID는 참조 관계까지 같을 때만 동등하다고 판정한다.

| 다른 방향 | 판단 |
| --- | --- |
| 기존 PSNR·문자 유사도 문턱 낮추기 | 무엇이 보존됐는지 설명하지 못하므로 채택하지 않음 |
| 모든 형식을 공통 문서 모델로 재작성 | 장기적으로 가능한 별도 제품 투자. 48건을 판정하기 위한 선행 조건으로는 과도함 |
| 알려진 내용의 입력 + 형식별 의미 검사 + 기존 비교 보존 | 우선 권장. 기준선 오류와 실제 회귀를 함께 발견할 수 있음 |

**채택 기준:** 48건 각각을 실제 손실·허용된 생성 차이·기준선 문제·미확인으로 근거와 함께 설명한다. 미확인은 PASS로 바꾸지 않는다. 기존 raw 결과와 문턱값은 남긴다.

| 후보 | 기대 효과 | 확인된 제한·미확인 사항 |
| --- | --- | --- |
| resvg + usvg, PDF에는 krilla-svg/krilla | SVG 해석과 글꼴·리소스 처리 기준을 래스터와 PDF에 공유할 수 있는 후보 | resvg의 `direction`·`unicode-bidi`·외부 SVG `use` 등 제한. 현재 krilla의 usvg/resvg 의존은 0.47 계열로 기존 0.49 실험과 다름 |
| macOS WebKit의 WKWebView에서 이미지·PDF 생성 | 브라우저의 문서 레이아웃을 사용하는 별도 방향. Apple이 이미지·PDF 생성 API를 제공함 | 현재 FileToX에서 미실험. 글꼴·이미지 로딩 완료, 투명도·크기·벡터 유지, macOS 15와 최신 OS의 차이, 작업 취소·메모리 확인 필요 |
| 현재 CoreSVG/Skia + 기능별 수제 보정 확대 | 작은 범위의 즉시 개선에 유리 | 이미 잘 되는 기능과 깨지는 기능이 엇갈림. 주 해결 전략으로 확대하면 예외 처리가 늘어남 |

`svg2pdf`는 조사일 현재 저장소가 보관 상태이며 유지 관리자가 krilla/krilla-svg를 안내한다. 새 도입 후보는 안내된 후속 프로젝트를 기준으로 평가한다. krilla-svg는 usvg 트리를 받아 PDF에 그리며 텍스트 삽입과 필터의 비트맵 변환을 구분한다. 이 API가 있다는 사실은 FileToX의 벡터 PDF 동등성이나 PDF/A 적합성이 검증됐다는 뜻이 아니다.

**실험의 선택 순서:**

1. 공통 글꼴과 안전한 리소스 로더를 정한 뒤, 기존 68개 SVG 및 부족한 RTL·세로쓰기·복잡한 참조 표본을 고정한다. 후보와 독립적인 기대 결과를 먼저 정하고 현재 경로도 대조군에 넣는다. 보존된 결과는 읽기만 하며 과거 host/helper를 재실행하지 않는다.
2. resvg 계열과 WebKit 두 후보의 최종 PNG·PDF를 같은 크기에서 비교한다. 변환에 필요한 정리만 하고, 현재 CoreSVG를 위한 텍스트 윤곽선 보정을 무조건 새 렌더러에 먼저 적용하지 않는다. WebKit 자체를 자동으로 정답으로 삼지 않는다.
3. 필수 문자 방향·세로쓰기 표본을 resvg가 처리하지 못하면 resvg 단독 주 경로는 탈락이다. WebKit이 필수 표본과 최소 OS 기준을 충족하면 주 경로 후보로 삼는다.
4. 일반 정적 SVG의 재현성과 버전 고정이 우선이고 resvg 계열이 필수 표본을 충족하면 그 계열을 선택한다. krilla와 호환되는 usvg 버전을 먼저 고정해야 하며 현재 0.49 실험 결과를 다른 버전의 근거로 재사용하지 않는다.

공통 해석기는 이름만 같아서는 안 된다. 한 번 만든 같은 `usvg::Tree`를 resvg와 krilla의 `draw_svg`에 전달해, 서로 다른 usvg 버전이 조용히 각자 해석하는 구조를 피한다. 이 선택은 resvg 업데이트를 krilla의 호환 버전과 함께 관리해야 한다는 비용이 있다. `embed_text=true`도 다음 문서 단계가 올바른 문자를 읽는다는 보장은 아니므로 실제 읽기 결과를 검사한다. PDF로 표현할 수 없는 필터의 비트맵 처리는 해상도를 명시한 예외로 관리한다.

**채택 기준:** 글자·참조 그림의 누락, 잘림, 새 빈 출력은 허용하지 않는다. 최종 크기의 투명 결과, 흰색·검은색 배경 합성, PDF의 실제 벡터·이미지 구성을 확인한다. 기존 엄격 점수는 유지하며 규격상 올바른 차이는 별도 근거로 설명한다. 글꼴과 리소스가 같은지 먼저 확인한다. 두 후보 모두 실패하면 실패 표본을 남기고 그 기능만 다음 조사 대상으로 삼는다. 새로운 범용 SVG 엔진을 직접 만드는 일로 확장하지 않는다.

WebKit 실험은 사용자 브라우저 세션을 사용하지 않는 앱 내부 렌더링 helper 설계다. SVG를 문서로 여는 방식과 HTML의 이미지로 넣는 방식의 글꼴·참조 이미지 처리가 같은지 확인한다. 공개 API만으로 투명도·픽셀 크기·색공간을 충족해야 하며 비공개 API가 필요한 후보는 채택하지 않는다. 네트워크, 스크립트, 임의 파일 접근을 제한한 정적 렌더링과 로드 완료·시간 제한을 함께 확인해야 한다. 파일 읽기 범위 제한 API 하나만으로 외부 요청이 모두 막힌다고 가정하지 않는다. 취소·메모리 관측에는 WebContent 등 렌더링에 참여하는 자식 프로세스도 포함한다.

## 4. AVIF: 두 후보의 상시 경쟁을 정상 변환 경로에서 분리

현재 실행 순서는 `ImageIO 인코딩 → native 인코딩 → 두 결과 디코딩 → 색·알파 SSE 및 메타데이터 비교 → 선택`이다. 3개 입력의 전체 변환은 약 1.08·1.97·1.52초였고 같은 host의 ImageIO 전용 경로는 약 0.28·0.41·0.28초였다. 네이티브 4:4:4의 색 보존 개선이 있지만 두 번의 인코딩 비용도 지불한다. [AvifEncoder](../../Sources/Engine/Engines/Images/AvifEncoder.swift)

권장하는 장기 정상 경로는 `입력 준비와 보존 항목 확정 → 입력·품질 정책에 따라 인코더 선택 → 한 번 인코딩 → 출력 유효성·보존 항목 확인`이다. 두 인코더의 경쟁 비교는 개발·회귀 검사에 남긴다. 실패 시 한정된 대체 경로를 허용할 수 있지만 취소를 실패로 취급해 재시작해서는 안 된다.

기존 동작도 구분해야 한다. 다음 표는 코드로 확인한 현재 동작이며 새 정책이 아니다. [호출부](../../Sources/Engine/Engines/Images/ImageEncoder.swift)는 `try AvifEncoder.improve`의 오류를 전달한다.

| 조건 | 현재 동작 |
| --- | --- |
| helper 없음, 대상 입력 조건 미충족 | ImageIO 파일 유지 |
| 품질 또는 메타데이터 가드 불합격 | ImageIO 파일 유지 |
| ftyp는 통과했지만 디코드 불가·크기 불일치 | 후보 오류 계산이 실패해 ImageIO 파일 유지 |
| helper 비정상 종료·출력 파일 없음·잘못된 ftyp | 오류 전달 |
| 취소·시간 초과 | 오류 전달 |

모든 helper 실패가 이미 자동 fallback된다고 가정하지 않는다. 회귀 검사에는 실제 사용한 인코더와 후보를 버린 이유를 기록해 helper 결함을 성공으로 가리지 않는다. 취소 후 새 인코딩을 시작하지 않는다. 시간 초과 뒤 이미 만들어진 ImageIO 파일을 채택하는 것과, 단일 인코딩 구조에서 ImageIO를 새로 시작하는 것은 비용·마감 시간이 다른 정책이다. 이 둘을 별도로 정한다.

다만 **현재 보장과 동일하지 않다.** 현재 가드는 각 입력에서 ImageIO로 읽은 색·알파 SSE가 ImageIO 결과보다 악화되지 않는 후보만 선택한다. 유한한 회귀 표본을 통과한 단일 인코더가 모든 새 입력에서 이 관계를 지킨다고 증명할 수는 없다. 같은 개별 입력 보장을 유지하려면 경쟁 비교 비용도 남는다.

안전한 이행은 다음과 같다.

1. 회색조·고정밀·다중 프레임·메타데이터 제한을 명시하고 선택 경로를 결정한다. 속도 우선과 색 세부 보존 우선의 정책이 필요하면 사용자에게 의미 있는 품질 설정으로 표현한다.
2. AVIF용 메타데이터 준비를 개선한다. 현재 EXIF는 1픽셀 JPEG의 APP1로 직렬화돼 64KB 한계가 있고, 긴 EXIF는 후보를 만든 뒤에야 버리게 된다. 이 경로를 그대로 두고 품질 가드를 삭제하지 않는다. [메타데이터 준비](../../Sources/Engine/Engines/Images/WebpJxlEncoders.swift)
3. 검증된 입력 범위부터 단일 인코딩을 별도 경로로 시험한다. 소스 대비 색·알파, ICC·EXIF·XMP, 방향·크기·프레임 수를 확인한다. 불확실한 입력은 기존 가드 경로를 유지한다.
4. 선택 경로가 안정된 뒤 복사·버퍼·동시 작업 예산을 최적화한다. helper의 스레드 수와 앱의 동시 작업 수를 함께 다룬다.

| 다른 방향 | 판단 |
| --- | --- |
| 후보 비교 유지 + 버퍼 재사용 | 현재 개별 입력 보장을 유지한다. 구조적 추가 비용은 남음 |
| 검증된 입력 범위에 단일 인코딩 | 비용을 줄이는 가장 직접적인 구조 변화. 보장의 변화와 미지원 범위를 명시해야 함 |
| 코덱이나 이미지 엔진 전체 교체 | 후보를 두 번 만드는 구조를 그대로 두면 중복 비용은 남음. 현재 선택보다 낫다는 실제 측정이 필요 |

**채택 기준:** 기존 161개 이미지 표본과 메타데이터·회색조·저품질·알파·대형 이미지 경계를 검사한다. 목표와 속도 개선 폭은 새 측정으로 정한다. host와 helper의 메모리는 같은 시간축에서 관측하며 서로 다른 시점의 최대값을 합쳐 실제 총 메모리라고 하지 않는다. 작은 파일 몇 개의 평균 속도만으로 대형 이미지 정책을 결정하지 않는다.

## 구현에 들어가기 전 확정할 것

## 독립 검토

Claude-dev-max의 `claude-opus-5-5`, effort `max`의 1차 독립 검토를 받았다. 기능·내용·보존 규약을 분리하고, 관리형 FFmpeg·제한된 SVG 주 렌더러·AVIF 단일 인코딩을 검증하자는 큰 방향은 일치했다. PMLZ 이름 불일치·한글 제한·SVG→ODT의 중간 텍스트 손실은 부모가 공식 소스·현재 코드·보존 JSON으로 대조했다.

1차 의견의 모든 문장을 그대로 채택하지는 않았다. 이미지→TXT와 그림을 포함하는 문서 출력을 구분했고, 미확인 PPTX 본문 손실은 가설로 남겼으며, AVIF helper 오류와 품질 가드 거부도 구분했다. 2차 검토에서도 이 정정에 동의했고, 디코드 불가 후보의 조용한 대체, 기존 ImageIO 파일 재사용과 재인코딩의 차이, 공통 usvg 트리 강제, 현재 경로를 포함한 SVG 대조군, WebKit 공개 API·자식 프로세스 검증을 추가했다.

두 검토는 같은 Claude-dev-max / Opus 5.5 / max 설정으로 수행했다. 17건의 ID 분포는 부모가 보존 JSON에서 직접 확인했으며, 2차 검토는 해당 JSON을 재확인하지 못했다. SVG 후보의 성능·범용 지원·최소 OS 동작은 어느 검토에서도 실증하지 않았다. 위 채택 조건을 충족한 뒤에만 주 경로 전환을 결정한다.

WebKit 문서는 부모의 Context7 조회로 확인했다. Claude 환경에는 Context7 CLI가 없어 FFmpeg·Calibre는 공식 문서·소스로 확인했다. 이번에는 제품 코드·의존성 변경, 새 변환·빌드·성능 시험, 실기·배포 검증을 수행하지 않았다.

## 같은 날의 구현 후속

위 조사를 마친 뒤 별도 요청으로 PML 어댑터·문자 손실 거부, TS의 동일 시점 재시도, 슬라이드 본문·FB2 텍스트 상자 누락, 생성 PDF의 텍스트 전용 중간 경로와 실제 FFmpeg 안내를 수정했다. 조사 당시 가설이었던 슬라이드 누락도 보존 입력과 새 검사로 확인했다. 구현·검토·실패 시도·현재 검증 범위는 [변환 버그 후속 기록](../design/engine-differential-triage.md#conversion-bug-follow-up-2026-10-27)에 구분한다. 이 후속 작업이 관리형 FFmpeg, 새 SVG 엔진, AVIF 정책 변경이나 5번 실기·배포 검증까지 완료한 것은 아니다.
